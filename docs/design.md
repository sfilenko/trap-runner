# Trap Runner — дизайн

- **Дата:** 2026-10-01
- **Статус:** v3 — після незалежного рев'ю і звірки з демо-репо курсу (розділ 13)
- **Контекст:** capstone курсу «Crash Course: Agentic Engineering» (fwdays, вересень 2026)

## 1. Мета

Невеликий браузерний платформер: пастки-тролінг у стилі Level Devil плюс скролінг, вороги й монети з Super Mario.

Проєкт має дві мети:
1. Гра працює і проходиться від першого до останнього рівня.
2. Кожна застосована практика курсу має доказ, який можна відкрити: файл, коміт, тест, прогін, запис. Джерело вимог — `RUBRIC.md` репозиторію capstone.

Обсяг коду і кількість практик не оцінюються. Оцінюється те, що кожну названу практику видно. Звідси правило проєкту: **маленька гра, докази збираються під час роботи, а не після**.

### Критерій «готово»

- Гра в браузері проходиться від рівня 1 до останнього.
- `pnpm check` повертає exit 0. `pnpm e2e` повертає exit 0. CI зелений.
- Є відео на 1–2 хв і PR у форку capstone за шаблоном.

## 2. Обсяг

**Входить у MVP:**
- один персонаж: біг ліворуч і праворуч, стрибок;
- 3–5 коротких рівнів фіксованої висоти, ширина довільна;
- горизонтальний скролінг камери;
- 3 дії пасток (розділ 5);
- один тип ворога: патруль між двома точками; знищується стрибком зверху;
- монети, рахунок, лічильник смертей;
- графіка з прямокутників;
- екран перемоги з рахунком і кількістю смертей.

**Не входить:** звук, спрайти й анімації, power-up'и, кілька типів ворогів, збереження прогресу, меню налаштувань, мобільне керування, редактор рівнів, пошуковий солвер рівнів.

## 3. Стек

TypeScript, Canvas 2D, Vite, Vitest, Playwright, zod (схема рівня), OpenSpec `1.13.0` (devDependency, `--save-exact`). Node ≥ 22.12 (вимога Vite 8 і Vitest 5; на Node 22.3 Vitest не стартує), pnpm (через corepack): скрипти курсу (`openspec-pin`, `spec-check`, `hooks-selftest`) розраховані на pnpm.

Свого рушія немає. Фізика — власна AABB, бо детерміноване ядро без браузера — основа всієї перевірки.

## 4. Архітектура

Уся логіка гри — одна чиста функція `step(world, input) → world`. Усе інше — тонкі адаптери.

```
src/
  core/        чисте ядро: без DOM, без Math.random, без Date
    types.ts     World, Player, Enemy, Trap, Coin, InputFrame, GameEvent
    world.ts     createWorld(level) → World
    step.ts      step(world, input) → World    (1 тік = 1/60 с)
    physics.ts   гравітація, стрибок, AABB-колізії з тайлами, суб-кроки
    traps.ts     тригери, затримки, дії
    enemies.ts   патруль, стрибок зверху, удар збоку
  render/      Canvas: малює World; камера
  input/       клавіатура → InputFrame { left, right, jump }
  main.ts      ігровий цикл: фіксований крок з акумулятором → step → render
levels/        level-NN.json, level-NN.solution.json, level.schema.ts
tools/         validate-level (CLI на Node)
scripts/       check-boundaries.mjs, level-loop.mjs
tests/         unit/, replay/, e2e/
```

**Рішення:**
- **Фіксований крок 60 тіків/с.** Рендер працює з будь-якою частотою кадрів. Логіка детермінована, тому replay дає однаковий результат на будь-якій машині.
- **`World.events[]`.** Кожен тік ядро повертає події цього тіку: `trapTriggered`, `coinCollected`, `enemyStomped`, `died` (з `cause`: `spikes` | `pit` | `enemy`), `levelComplete`. Тести перевіряють події, а не пікселі.
- **Межа `core/` захищена механічно. Список заборон живе в одному місці:** `scripts/check-boundaries.mjs`. Заборонено імпорт `render/` чи `input/`, а також `window`, `document`, `Math.random`, `Date` у `src/core/**`.
  - Гейт викликає скрипт для всього `src/core/` і падає з exit 1.
  - PreToolUse-hook `guard-core` викликає той самий скрипт для вмісту правки агента і блокує правку ще до запису.
- **Dev-хук стану.** У dev-збірці `window.__game` віддає поточний `World` лише для читання. Його використовують e2e-тест і Playwright MCP. У production-збірку він не потрапляє.

## 5. Модель рівня

### Формат

```json
{
  "id": "level-01",
  "tiles": [
    "..........................",
    "..o.......................",
    "S...................^...G.",
    "##########################"
  ],
  "enemies": [{ "id": "e1", "x": 10, "y": 2, "patrol": [8, 14], "speed": 1 }],
  "traps": [
    { "id": "t1",
      "trigger": { "kind": "zone", "rect": [15, 0, 2, 4] },
      "action":  { "kind": "removeTiles", "rect": [17, 3, 3, 1] },
      "delayTicks": 6 }
  ]
}
```

- Тайли: `.` порожньо, `#` тверде, `^` шипи, `o` монета, `S` старт, `G` фініш. Вороги задаються лише в `enemies[]`.
- Розмір тайла: 16 px. Висота рівня: 15 тайлів. Ширина: довільна.
- Усі координати і `rect: [x, y, w, h]` у JSON задаються в тайлах. `speed` ворога — у пікселях за тік. Ворог має `x` і `y` (тайл, на якому він стоїть).
- Id монети виводиться з її позиції: `c<x>_<y>` (наприклад, `c2_1`). На цей id посилається тригер `event: coinCollected`.

### Пастки: тригер + дія

| Тригер | Умова |
|---|---|
| `zone` | хітбокс гравця перетинає `rect` |
| `event` | сталася подія: `coinCollected` з `id` або `enemyStomped` з `id` |

| Дія | Ефект |
|---|---|
| `removeTiles` | тверді тайли в `rect` зникають (провалля) |
| `addSpikes` | у `rect` з'являються шипи |
| `moveGoal` | фініш переміщується в `to: [x, y]` |

- Пастка спрацьовує **один раз за спробу**. Дія виконується через `delayTicks` тіків після тригера (0 = у тому ж тіку).
- Якщо кілька пасток спрацьовують в одному тіку, вони обробляються в порядку масиву `traps[]`.
- Монета-приманка — це звичайна монета плюс пастка з тригером `event: coinCollected`. Окремої механіки немає.

## 6. Правила гри

- **Смерть:** шипи, падіння нижче рівня, дотик ворога не зверху. Рівень одразу перезапускається: пастки, вороги і монети цього рівня скидаються. Життів немає. Лічильник смертей наростає і не скидається.
- **Стрибок зверху:** у поточному тіку гравець падає (`vy > 0`), а в попередньому тіку його нижній край був вище за верхній край ворога. Тоді ворог гине (`enemyStomped`), а гравець отримує відскок. Якщо в одному тіку виконуються і умова стрибка зверху, і умова удару збоку, **перемагає стрибок зверху**.
- **Стрибок:** спрацьовує лише на натисканні (перехід «не натиснуто → натиснуто») і лише на землі. Утримання кнопки не дає повторного стрибка після приземлення.
- **Фініш:** дотик до `G` → `levelComplete` → наступний рівень. Після останнього рівня — екран перемоги. Якщо смерть і дотик до фінішу стались в одному тіку, перемагає смерть.
- **Рахунок:** сума монет пройдених рівнів. Монети рівня, на якому гравець загинув, не зараховуються, поки рівень не пройдено.
- **Камера:** слідує за гравцем по горизонталі, обмежена краями рівня. Вертикального скролінгу немає.
- **Фізичні константи** (гравітація, швидкість, висота стрибка, відскок) визначає людина на етапі 2. Агент не змінює їх без явного дозволу (правило в `AGENTS.md`).

## 7. Перевірка

### Шари

| Шар | Що перевіряє | Інструмент |
|---|---|---|
| 1. Typecheck | типи | `tsc --noEmit` |
| 2. Boundaries | чистоту `src/core/` | `scripts/check-boundaries.mjs` |
| 3. Unit | фізику, пастки, ворогів, монети окремо | Vitest |
| 4. Replay + рівні | сценарії на справжньому `step()`; кожен рівень валідний і прохідний | Vitest + `tools/validate-level` |
| 5. E2E smoke | гра запускається, канвас малює, «вправо» рухає гравця, у консолі немає помилок | Playwright |

- `pnpm check` = шари 1–4, exit code.
- `pnpm e2e` = шар 5.
- Pre-commit hook запускає `pnpm typecheck && pnpm boundaries`, без тестів: курс вимагає коміт із червоним тестом перед зеленим, а повний `pnpm check` такий коміт заблокував би. GitHub Actions запускає `check` і `e2e`.

### Replay-тест

```json
{
  "scenario": "TRAP-collapse-01",
  "level": "fixtures/collapse.json",
  "inputs": [{ "ticks": 40, "right": true }, { "ticks": 30 }],
  "expect": [
    { "tick": 38, "event": "trapTriggered", "id": "t1" },
    { "tick": 52, "event": "died", "cause": "pit" }
  ]
}
```

- Натискання стиснуті в RLE.
- **Трасування:** id сценарію в OpenSpec = ім'я replay-файлу = назва тесту.
- **Порядок комітів на кожен сценарій:** сценарій у spec → червоний replay → код → зелений.

### Unit-тести на місця, де агент найімовірніше помилиться

- приземлення точно на край тайла;
- стрибок під стелю;
- тунелювання крізь стіну в один тайл на максимальній швидкості;
- стрибок зверху проти удару збоку в одному тіку;
- дві пастки в одному тіку.

### Перевірка рівнів

1. **Валідатор:** схема zod і семантика. Рядки однакової довжини, рівно один `S` і один `G`, висота 15, унікальні id, посилання тригерів існують, патруль у межах рівня, `rect` у межах рівня.
2. **Доказ прохідності:** `level-NN.solution.json` проганяється через `step()` і дає `levelComplete`. Під час проходження спрацьовує щонайменше одна пастка і збирається щонайменше одна монета.

Розв'язки рівнів, які робить людина, записуються в dev-режимі: клавіша `R` починає і завершує запис і зберігає `solution.json`.

### Перевірка перевіряючого

Один раз навмисно ламаємо ядро (наприклад, вимикаємо колізію зі стелею) і фіксуємо, що replay-тести червоніють. Запис іде в `docs/autonomy-log.md`. Гейт, якого ніхто не бачив червоним, не рахується як доказ.

### Межі перевірки (чесно вказуємо в PR)

Автоматично не перевіряються: «відчуття» стрибка, складність і справедливість рівнів, візуальна читабельність. Доказ прохідності показує, що рівень *можна* пройти записаним розв'язком, але не те, що він цікавий чи що інші шляхи проходження теж працюють. Це ручні перевірки, рішення приймає людина.

## 9. Практики курсу → докази

| Практика | Доказ |
|---|---|
| Контекст-інженерія | статичний: рядок PreToolUse без Post в `.agent-log/actions.jsonl` + рядок з тим самим `id` в `.agent-log/blocked.jsonl` (яке правило спрацювало). Динамічний: вивід Playwright MCP (стан + скріншот). Лише для курсу (ДЗ дня 02): `docs/context-log.md` з трьома колонками (`/context` до → одна зміна → після → той самий промпт у свіжій сесії) |
| SDD | `openspec/` і `docs/intent.md` закомічені раніше за код; одна зміна спеки, коли реальність не збіглася |
| Верифікація | коміти «червоний replay → зелений»; прогін CI; запис про навмисну поломку ядра |
| maker ≠ checker | звіт `game-checker` і що він знайшов; незалежне рев'ю цього дизайну (розділ 13) |
| Оркестрація (лише для курсу, ДЗ дня 04) | контракт (`core/types.ts` + схема рівня) закомічений до fan-out; два worktree; фактичні витрати — в `docs/intent.md` |
| Цикли | `scripts/level-loop.mjs` + лог одного прогону |
| Журнал довіри | `docs/autonomy-log.md` з рядком зниження рівня (фізичні константи, складність рівнів) |

### Цикл генерації рівнів

`node scripts/level-loop.mjs --level NN --max-iter 5`:
1. Викликає `claude -p` з промптом зі skill `make-level` і обмеженням `--max-turns`.
2. Запускає `tools/validate-level` на результаті.
3. Якщо валідація не пройшла, передає агентові текст помилки і починає наступну ітерацію.
4. Зупиняється на першому успіху або на ліміті ітерацій.
5. Кожна ітерація пише рядок у `.agent-log/loops/<timestamp>.jsonl`: номер ітерації, результат, помилки, тривалість.

## 11. Що вирішує людина

- стек і архітектура (цей документ);
- фізичні константи і «відчуття» керування;
- набір пасток, дизайн і складність рівнів;
- які знахідки `game-checker` прийняти, а які відхилити;
- коли підвищити або знизити рівень довіри;
- усі коміти і push.

## 12. Ризики

| Ризик | Що робимо |
|---|---|
| Фізика з'їдає бюджет | константи фіксує людина один раз; тюнінг обмежено 1 год |
| Три механіки від Маріо розширюють обсяг | один тип ворога, лише горизонтальна камера; решта — поза MVP |

| Агент генерує тривіальні рівні в циклі | вимоги «≥1 пастка спрацювала, ≥1 монета зібрана» у валідаторі; фінальне рішення про рівень — за людиною |

## 13. Рев'ю дизайну

**v1 → v2.** Автор v1 — агент, який вів розмову з людиною. Рецензент — окремий агент `agentic-advisor` (лише читання). Він бачив тільки цей файл і базу знань курсу, розмови не бачив. Обмеження рецензента: він не відкрив `RUBRIC.md` і працював за конспектом слайдів s.338–341.

| Знахідка рецензента | Рішення людини |
|---|---|
| пошуковий солвер дублює `solution.json` | прибрано |
